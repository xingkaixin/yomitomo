## macOS 首发与后续版本

| 升级路径 | 预期行为 |
| --- | --- |
| 0.15.1 及更早版本 → 0.16.0 | 旧更新器读取 `latest-mac.yml` 并下载完整 ZIP，安装重启后切换 Sparkle |
| 0.16.0 → 下一个正式版本 | 若差分生成成功且适用，Sparkle 下载差分；否则使用签名完整 ZIP |
| 更早的 Sparkle 版本 → 最新版 | 最近两个符合条件的历史版本用于差分生成；无匹配差分时使用完整 ZIP |
| 尚未迁移的旧版 → 后续最新版 | 继续使用旧 manifest 和完整 ZIP，不要求先安装 0.16.0 |

0.16.0 没有历史 Sparkle 基线，只有完整 ZIP 和 `appcast-mac-arm64.xml`，没有 `.delta`
是正常结果。后续差分大小取决于实际改动，不能把历史实验约 48 MB 当成本版下载大小。
Windows 仍使用 NSIS 与 electron-updater。

## 草稿产物与公开顺序

1. 确认上述门禁后，对目标提交打 `v0.16.0` tag 并推送。Release workflow 构建两平台并创建 GitHub Release 草稿。
2. 确认签名、公证检查通过，替换草稿正文。核对下列产物齐全、版本一致：
   - macOS：`Yomitomo-0.16.0-mac-arm64.dmg`、`Yomitomo-0.16.0-mac-arm64.zip`、ZIP blockmap、`latest-mac.yml`、`appcast-mac-arm64.xml`。
   - Windows：`Yomitomo-0.16.0-win-x64.exe`、对应 blockmap、`latest.yml`。
3. 核对 appcast 仅公告 0.16.0，完整 ZIP URL 指向本版本代理路径，含 Ed25519 签名且长度与 ZIP 一致。核对 YAML 版本、文件名、大小与哈希。
4. 公开 Release 并确认为 latest。Worker 的 `/updates/appcast-mac-arm64.xml` 和 YAML 读取 latest；草稿阶段无法通过这些地址验收新包。
5. 执行 [发布后 smoke check](../release-guide.md)。除 macOS 外检查 `/latest.yml`、`/updates/latest.yml` 与 Windows 安装包。使用 GET 核对版本与内容，不能只看 HEAD 状态码。
6. 部署官网（`pnpm deploy:cf`），确认三语 `/release-notes/{locale}/0.16.0.json` 和 changelog 可访问。官网安装包链接由桌面版本号生成，正式包可下载后再部署，避免新链接先指向不存在的产物。
7. 用真实已安装的旧版执行一次升级，确认完整 ZIP 下载、安装重启、版本变成 0.16.0、书库与设置保留；再确认 Sparkle 检查可读取 feed 且不自动下载。检查三语更新说明可显示。
8. 完成检查后再对外公告。记录执行结果、发布 workflow 与验收证据。

## 下一次发布起每次检查

- 保留至少最近两个 Sparkle 正式版本的 ZIP 和 appcast；不要删除、改名或覆盖已公开产物。
- 查看差分生成日志，确认选中了预期基线。脚本只检查最近 30 条 Release；草稿和预发布太多时可能把基线挤出查询范围。
- 从生成的 XML 读取实际 delta 名称、来源版本、签名和长度，并确认对应文件已上传；不要猜测文件名或手改 XML。
- 对完整 ZIP 和实际 delta URL 做 GET/Range 检查。请求 `Range: bytes=0-1023` 应返回 `206`，`Content-Range` 应以 `bytes 0-1023/` 开头。
- 用上一正式版验收真实差分安装与重启；无适用差分的版本仍应能通过完整 ZIP 更新。继续保留 YAML、ZIP 和 blockmap，保证未迁移旧客户端可直接升级。
- 若正式发布发现问题，修复后递增版本重新签名发布。同名文件在 Worker 可缓存一年；workflow 重跑有 `--clobber` 行为，不应用于覆盖已公开版本。
