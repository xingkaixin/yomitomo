# 批注卡片性能观测

本轮只增加可复现的观测脚本和报告，没有修改卡片运行逻辑或加入虚拟化。
在这份长文本数据中，500～1,000 条批注已经产生明显的响应延迟。滚动成本主要在
脚本执行，CPU profile 指向 React 渲染和逐卡时间格式化，布局计算占比较小。

## 方法

2026-10-02，macOS arm64、Apple M1 Pro、Electron 44.5.0、Chromium
152.0.7977.130。使用 `3204d400` 对应的桌面构建，通过 Playwright 操作真实 Electron
窗口，视口固定为 1,500 × 860 CSS 像素。

- 通过导入界面建立三篇 Markdown 文章，每篇都是相同的 1,000 段英文文本。
  测量的是文本文件导入后的长文本阅读器，不包括 EPUB、PDF 和微信读书。
- 关闭隔离的测试应用，再向测试数据库分别写入 100、500、1,000 条均匀分布的批注。
  每条批注引用一整段文本，包含一条想法，时间均设为一天前。
- 每组采样三轮。每轮重置阅读位置为开头、字号为 20 px、内容宽度为 600 px，并重新加载页面。
  数据准备不计入耗时；测试数据库内写入新鲜的模型价格缓存，避免独立的启动刷新干扰测量。
- 打开：点击书库条目，等待正文、全部批注的高亮锚点、字体和两个动画帧。
- 滚动：连续执行 20 次即时滚动，每次移动阅读视口高度的 75%，每步等待两个动画帧。
- 字号：通过实际工具栏将字号从 20 px 调为 21 px，再等待两个动画帧。

操作耗时 `readyMs` 包含 UI 自动等待，不等于纯渲染耗时，也不保证所有后续工作已经结束。
每个阶段结束后再请求等待 500 ms，采集这个完整观察窗口内的 CDP 脚本、布局、样式与任务时间，
以及浏览器长任务和动画帧间隔。忙碌的事件循环可能使尾窗超过 500 ms。
这些探针也有少量开销；CPU profile 使用独立的一轮，不混入下面的基线。

## 三轮中位数

所有时间单位为 ms。“最长任务”是每轮观察窗口内最长任务的三轮中位数；0 表示没有
被 Long Tasks API 记录的长任务，不表示没有脚本执行。Script 和 Layout 来自包含尾窗的
CDP 度量，与操作耗时的统计窗口不同。

| 批注数 | 操作 | 操作耗时 | Script | Layout | 最长任务 | 最大帧间隔 |
| ---: | --- | ---: | ---: | ---: | ---: | ---: |
| 100 | 打开 | 411.4 | 262.7 | 62.3 | 136 | 168.6 |
| 100 | 滚动 20 次 | 663.5 | 457.2 | 1.3 | 0 | 18.7 |
| 100 | 调整字号 | 428.9 | 93.9 | 28.0 | 72 | 66.7 |
| 500 | 打开 | 1,535.1 | 1,149.9 | 129.3 | 481 | 533.3 |
| 500 | 滚动 20 次 | 2,618.4 | 2,408.1 | 2.3 | 130 | 150.0 |
| 500 | 调整字号 | 927.8 | 489.8 | 32.3 | 246 | 300.1 |
| 1,000 | 打开 | 2,559.1 | 1,780.4 | 224.0 | 957 | 1,050.0 |
| 1,000 | 滚动 20 次 | 4,960.3 | 4,603.7 | 2.3 | 251 | 266.7 |
| 1,000 | 调整字号 | 1,924.4 | 1,142.6 | 40.4 | 701 | 850.1 |

动画帧间隔用于发现停顿，不能直接换算成实际显示 FPS。只有三轮采样，本报告不推断 P95。

打开后和滚动后，所有卡片都仍然挂载：

| 批注数 | 挂载卡片 | 高亮片段 | 页面 DOM 元素 |
| ---: | ---: | ---: | ---: |
| 100 | 100 | 400 | 4,700 |
| 500 | 500 | 2,000 | 18,700 |
| 1,000 | 1,000 | 4,000 | 36,200 |

字号增大后，每段引文从四行变为五行，1,000 条批注对应 5,000 个高亮片段和 37,220 个
DOM 元素。这说明卡片和高亮规模都随批注量增长，但仅凭 DOM 数量不能确定优化方案。

## 滚动 CPU profile

独立采集 1,000 条批注、同样 20 次滚动的一轮 V8 CPU profile。采样覆盖约 6,268 ms；
它还包含采集边界上的少量工作，因此不与基线直接比较。

| 调用 | 含子调用的采样时间 ms | 自身采样时间 ms |
| --- | ---: | ---: |
| React `performWorkUntilDeadline` | 4,385.9 | 1.5 |
| React `renderRootSync` | 3,555.6 | 0.0 |
| `ReaderRelativeTime` | 963.1 | 192.5 |
| `formatDateTimeValue` | 654.6 | 654.6 |

这些调用存在包含关系，不能把各行相加。独立采样的 CDP Layout 为 2.7 ms。
源码中，`reader-surface-view.tsx` 会遍历批注轨道条目渲染 `AnnotationCard`；
`ReaderRelativeTime` 为提示内容调用 `formatTime`；共享的 `formatDateTimeValue` 每次
创建 `Intl.DateTimeFormat`。采样证据支持优先检查这些重复工作。

后续优化建议先分别验证：滚动状态变化能否减少未变卡片的重新渲染，以及相同 locale/options
能否复用日期格式化器。两者都应使用相同数据重新测量，并检查活动卡片、编辑状态与时间显示。
如果仍有明显瓶颈，再评估按视口挂载卡片，同时保留引文定位、卡片高度和滚动锚定行为。
本轮没有验证这些候选改动的收益，不能承诺它们能消除全部卡顿。

数据仅代表这台机器上的英文纯文本、单条想法和固定视口。不能外推到 EPUB/PDF、复杂讨论、
其他操作系统或设备，也不是硬件无关的性能门禁。

## 复现

从仓库根目录执行，运行时保持测试窗口可见，避免并行执行其他性能测试或构建：

```bash
pnpm --filter @yomitomo/desktop build
pnpm --filter @yomitomo/desktop exec vitest run --config e2e/performance/vitest.config.ts e2e/performance/annotation-cards.test.ts
YOMITOMO_ANNOTATION_PROFILE=1 pnpm --filter @yomitomo/desktop exec vitest run --config e2e/performance/vitest.config.ts e2e/performance/annotation-cards.test.ts
```

基线输出 `apps/desktop/e2e/ui/artifacts/annotation-cards-performance.json` 和各规模截图。
profile 模式只采集 1,000 条批注一轮，输出 `annotation-cards-profiled.json` 和
`annotation-cards-scroll.cpuprofile`，不覆盖基线 JSON。可在 Chromium DevTools 的
JavaScript Profiler 中加载 CPU profile。

输出目录不提交 Git。脚本使用临时应用数据目录，结束后清理；不读取真实书库。
它只检查测量数据存在及批注锚点数量，不设置机器速度阈值，也不加入默认测试命令。
